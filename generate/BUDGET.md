# 算力预算与设置偏离记录

论文的设置表和 limitation 一节从这里取材。每个偏离都记三样：**实测数字、
偏离了什么、代价落在哪个主张上**。没有实测数字支撑的偏离不写进这里。

---

## 硬件

单张 **RTX 4090（24GB）**。**不能加卡、不能换卡**——这是外部约束，
不是可以优化掉的东西。下面所有取舍都由这一条推出来。

## 实测（TI2V-5B，官方 720p 设置）

| | |
|---|---|
| 配置 | 1280×704，121 帧 @24fps，50 步，bf16 |
| 速度 | **536 s/视频**（去噪 50 步 × 9.25 s/it = 462s，占 86%） |
| 峰值显存 | **14.55 GB / 24 GB**（`--offload` + VAE tiling） |
| 权重下载 | 一次性 1h36m（未设 HF_TOKEN，匿名限速） |
| 确定性 | **max \|Δpixel\| = 0.000000** |

两条推论：

1. **瓶颈是算术不是显存。** 峰值只用了 60%，省显存的手段（sequential offload、
   更激进的 tiling）一分钟都省不下来。能动的只有**分辨率**和**步数**。
2. **加载一次要 17s，下载是一次性的。** 长跑的开销全在去噪上，
   分 shard 或分批重启的固定成本可以忽略。

### 显存还剩一半，但没法换成时间

480p 峰值 11.66 / 24 GB。空出来的 12GB 不能直接变成速度：

- **去掉 `--offload` 不行**。文本编码器（umT5-XXL）+ transformer(5B) + VAE
  全常驻仍然超过 24GB，这正是第一次 OOM 的原因。
- **同卡跑两个进程**理论上装得下（11.66×2 = 23.3GB），但峰值是瞬时的，
  两个进程的峰值撞上就 OOM，8 天的长跑赌不起。

唯一实在的优化是**预算好文本嵌入**：16×37 个 prompt 只有 592 条，
一次性编码存盘，之后 pipeline 不加载文本编码器，transformer 可以常驻不换入换出。
offload 的传输开销约占 208s 中的 43s（50 步纯去噪是 165s），**省下来约 20%，
8 天 → 6.4 天**。代价是要改生成路径、要验证 `prompt_embeds` 走通。
目前**不做**——8 天已经可执行，而这个改动引入的 bug 风险要用整批数据来赔。
如果后面算力更紧（比如要加第三个模型），再回头做。

### 确定性这条要写进论文

同一 `(prompt, seed)` 生成两次，像素**逐位相同**。这不是"差不多"，是 0。

整个设计的可识别性建立在"种子固定视频、item 内唯一的差异源是文本"之上。
如果 attention kernel 非确定，item 内的条件差里就掺着采样噪声，
所有条件对比都要打折。现在这个前提是**验过的**，不是假定的。

复现：`--determinism-check`，产物在 `videos/<model>/_checks/determinism.json`。

## 账单

生成子集 37 items × 17 conditions × 3 seeds = **1887 视频/模型**
（15 → 17 是把下锚 `paraphrase_min` 与长度控制 `filler` 加回视频侧，
两者各自的理由见 `README.md` 与 `PILOT_NOTES.md`）。

| 配置 | s/视频 | 峰值显存 | 单模型 | 两个模型 |
|---|---|---|---|---|
| 720p / 50 步（官方默认） | 536 | 14.55 GB | 248 h ≈ **10.3 天** | **20.6 天** |
| **480p / 50 步** | **208** | **11.66 GB** | 109 h ≈ **4.5 天** | **9.1 天** |
| 480p / 50 步 / 2 种子 | 208 | 11.66 GB | 73 h ≈ 3.0 天 | 6.1 天 |

480p 实测 **2.58×** 提速（1280×704 → 832×480，像素数 0.44×；
提速略高于像素比，因为注意力对 token 数是超线性的）。

**定稿：480p / 50 步 / 3 种子 / 2 个模型 ≈ 9.1 天。**
只砍了优先级表里第 1 项，步数、种子数、模型数、时长全部保留。

## 降配的优先级，以及各自的代价

按"对论文主张的损害从小到大"排：

| 砍什么 | 代价落在哪 | 为什么排这个位置 |
|---|---|---|
| **1. 分辨率 720p → 480p** | 画质普遍下降 | 480p 是这些模型**本来就支持的运行模式**。而且 OSCBench 自己 Table 6 就不齐（Open-Sora 那行是 768×768），"分辨率统一"本来就不是他们的做法 |
| **2. 种子 3 → 2** | 方差分解变弱，误差棒变宽 | 仍有重复，仍能分离 item 与 seed 方差，只是自由度少 |
| **3. 步数 50 → 25** | 画质下降，且**低于默认步数不是任何官方模式** | 这是评测论文最难辩护的一种偏离：审稿人会问"模型做不到，还是你采样不足"。虽然 item 内所有条件受影响相同、组内对比仍成立，但跨模型绝对分的解释权会被质疑 |
| **4. 模型 2 → 1** | 失去"这不是某个模型的毛病"这句话 | OSCBench 有 6 个模型。降到 1 个，贡献从"模型普遍如此"退到"某模型如此" |
| ~~时长 121 帧 / 5s~~ | — | **不砍**。我们问的是"过程有没有走到完成"，时长就是构念本身，不是成本旋钮。省下的算力买不回这个 |

## 论文里怎么写这处偏离

一句话版本：

> 受单卡预算限制，我们在 832×480 而非各模型的 720p 默认分辨率下生成，
> 其余设置（帧数、时长、FPS、采样步数、引导强度）均为官方默认。
> 分辨率对所有条件一致，因此不影响本文赖以成立的 item 内条件对比。

三条支撑，按强度排：

1. **480p 是这些模型支持的运行模式**，不是我们发明的配置。
   HunyuanVideo-1.5 官方同时支持 480p 与 720p。
2. **OSCBench 自己的设置表就不齐**（Open-Sora-2.0 是 768×768，
   其余是 1280×720），"分辨率统一"本来就不是这一类工作的既定做法。
3. **本文的主张是 item 内条件差**，分辨率对同一 item 的 15 个条件完全相同，
   在组内对比中抵消。受影响的是跨模型绝对分，而那不是本文的主要结论。
